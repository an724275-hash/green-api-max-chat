# MAX Chat · GREEN-API

Минимальный клиент для текстовой переписки в **MAX** на React + TypeScript. Внешний вид вдохновлён веб-версией MAX: список чатов слева, переписка и редактор справа. Это учебный, неофициальный интерфейс.

## Быстрый запуск

Нужны Node.js 24.15+ в ветке 24 или Node.js 26+ и npm. Проверено локально на Windows, Node.js 26.7.0.

```bash
npm ci
npm run dev
```

Откройте адрес, который напечатает Vite (обычно http://127.0.0.1:5173).

Для проверки интерфейса без учётной записи нажмите **«Посмотреть демо без ключей»**. Введите номер формата `+7…` или `+375…`, создайте чат и отправьте текст. Демо работает целиком в памяти браузера и не обращается к GREEN-API; автоматический ответ явно помечен как имитация.

Переменные окружения для приложения **не нужны**. Не добавляйте ключи в `.env`, исходники, README, Git или сборку.

## Работа с настоящим MAX

1. В кабинете GREEN-API подготовьте **отдельный тестовый инстанс MAX** и авторизуйте его. Убедитесь, что это MAX, а не WhatsApp.
2. Для HTTP API оставьте `webhookUrl` пустым, включите `incomingWebhook: "yes"`. Для отражения исходящих сообщений и статусов включите `outgoingAPIMessageWebhook: "yes"`, `outgoingWebhook: "yes"`. При необходимости также включите `outgoingMessageWebhook: "yes"` для сообщений с телефона. Настройки меняются вами в кабинете; приложение их только читает.
3. Остановите другие потребители очереди этого инстанса. HTTP API извлекает события общей очереди и подтверждает их через `DeleteNotification`. Подтверждённые события удаляются из очереди безвозвратно. Неподдерживаемые события тоже подтверждаются, но не отображаются; для задания поддерживаются текст и статусы. Входящая очередь — не архив переписки.
4. Введите `idInstance`, `apiTokenInstance` и проверьте `apiUrl` по кабинету. По умолчанию указан официальный общий хост; кластерный адрес может отличаться. Адрес не вычисляется из номера инстанса. Допускаются HTTPS-хосты `api.green-api.com` и числовые `*.api.green-api.com`, необязательный старый суффикс `/v3` нормализуется.
5. Введите номер получателя в международном формате. Актуальный `CheckAccount` документирует номера РФ `7` + 10 цифр и РБ `375` + 9 цифр. Сервис вернёт внутренний строковый MAX `chatId`. Именно он используется для отправки и сопоставления ответов.
6. Отправьте текст и ответьте с телефона получателя. Ответ должен появиться автоматически. Сообщение «В очереди» означает принятие API, а не доставку; «Доставлено»/«Прочитано» устанавливаются только по событиям сервиса.

Ключ нужно вводить самостоятельно, только в своей доверенной локальной копии. Не передавайте ключ в переписке с помощниками, HR или в скриншотах.

## Команды и проверки

```bash
npm run lint       # ESLint
npm run typecheck  # TypeScript
npm test           # unit-тесты: API, события, reducer, polling
npm run build      # production dist/
npm run check      # lint + types + unit + build
npm run preview    # локальный просмотр production-сборки
```

Браузерные тесты:

```bash
npx playwright install chromium
npm run test:e2e
```

Если Chromium уже установлен, можно указать его путь (Linux):

```bash
CHROMIUM_PATH=/usr/bin/chromium npm run test:e2e
```

На Windows можно использовать установленный Microsoft Edge:

```powershell
$env:CHROMIUM_PATH = 'C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe'
npm run test:e2e
```

Playwright запускает изолированный headless-браузер и собственный Vite на порту 5178. Тесты адаптера перехватывают HTTP-запросы и возвращают фиктивные ответы; настоящие ключи и сообщения не используются. Все 9 сценариев прошли в Edge на Windows при повторной проверке 4 октября 2026. Три обновлённых снимка работающего интерфейса включены в `docs/screenshots/`.

В Windows sandbox этой проверки автоматическое закрытие тестового Vite зависало. После завершения тестов остановлен только запущенный ими процесс сервера; runner завершился с кодом 0. Подробности в отчёте.

## Архитектура

- `src/api/client.ts` — проверка ввода, доверенного API-хоста, HTTP-клиент, таймаут, безопасные ошибки, проверка ответов сервиса
- `src/api/poll.ts` — один последовательный цикл `receive → обработка → delete`; интервал минимум 1,1 с, long polling 25 с, backoff 2–30 с, отмена и восстановление после потери подтверждения
- `src/model/chat.ts` — чистый reducer, нормализация событий, объединение по `chatId + idMessage`, статусы до ответа POST и защита от устаревших статусов
- `src/hooks/useChat.ts` — жизненный цикл сессии, создание чата, отмена запросов, отправка без автоматического повтора
- `src/api/demo.ts` — отдельный локальный адаптер; реальный клиент не подменяется скрытно
- `src/App.tsx`, `src/styles.css` — формы, адаптивная переписка и состояния интерфейса

Чаты и черновики разделены по MAX `chatId`; при отключении все данные сессии удаляются из состояния приложения, запросы отменяются. Повторное создание известного номера не вызывает повторный `CheckAccount` в рамках сессии. HTTP 200 с логической ошибкой не считается успехом.

При сетевой ошибке отправки нельзя узнать, успел ли сервер принять POST. Автоматического повтора нет. Такая попытка отдельно помечается как неподтверждённая; если затем придёт API-событие, оно отображается как подтверждённое сообщение. Текстовые совпадения не используются для рискованного автоматического объединения.

## Безопасность и ограничения

- Ключи, чаты и сообщения не записываются в localStorage, sessionStorage, cookie, URL страницы или аналитику; внешних шрифтов/трекеров нет. Выход и обновление вкладки очищают историю
- Ключ присутствует в пути HTTPS-запросов к GREEN-API по контракту сервиса. Он виден владельцу браузера в DevTools и сервису; фронтенд не может сделать клиентский секрет невидимым. Строки в JavaScript нельзя гарантированно обнулить в памяти
- Не публикуйте приложение с встроенными ключами. Для промышленного продукта нужен backend с серверным хранением секретов, доступом пользователей и отдельной политикой хранения сообщений
- Запросы не перенаправляются на другой хост. Сырые тела ошибок/URL с ключами не выводятся в интерфейс и логи. Текст сообщений выводится средствами React, без `dangerouslySetInnerHTML`
- Отмена запроса браузером не отменяет уже принятую сервером отправку. Перед ручным повтором проверьте MAX
- Текст ограничен 4000 UTF-16 единицами, консервативно: emoji могут занимать две. Вложения, создание групп, загрузка истории, долговременное хранение, read receipts по просмотру и авторизация самого MAX по QR не входят в минимальный объём задания
- В рабочем аккаунте настройки приватности MAX и лимиты поиска могут не позволить `CheckAccount` найти человека. Приложение показывает ошибку, не перебирает номера и не выполняет обход
- Реальная работа браузерного CORS, сети, тарифа и конкретного аккаунта требует живой проверки. Публичный CORS-прокси не используется и не рекомендуется

## Что проверено, а что ещё нет

Фактические результаты локального прогона находятся в [docs/VERIFICATION.md](docs/VERIFICATION.md). Включённые скриншоты показывают форму подключения и демо; они не подтверждают живой MAX-обмен.

**Настоящий GREEN-API/MAX E2E не выполнялся:** действующие ключи и аккаунты не предоставлялись. Поэтому успешная доставка/ответ в живом MAX, CORS реального хоста и доступность конкретного инстанса не заявляются.

Проект подготовлен с AI-помощью (AI-assisted). Перед использованием как тестового задания кандидат должен проверить код и понимать решения. В доступном оригинальном PDF задания явного запрета AI нет. Репозиторий: https://github.com/an724275-hash/green-api-max-chat. Живой обмен GREEN-API/MAX не проверен; деплой и отправка работодателю не выполнялись.
