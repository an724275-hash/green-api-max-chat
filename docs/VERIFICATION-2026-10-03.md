## Failed при диагностике, затем исправлено

Demo chatId вычислялся по последним восьми цифрам телефона. Номера `+79991234567` и `+78891234567` создавали один чат. Новый браузерный regression-тест сначала получил 1 чат вместо 2. Теперь demo chatId использует весь нормализованный телефон; тест проходит. Реальный adapter использует chatId из CheckAccount.

## Ограничения среды

Первая установка зависимостей завершилась EPERM на общем npm-кэше вне writable workspace. Повтор с отдельным кэшем внутри рабочей папки прошёл.

Playwright выполняет тесты, но автоматическое завершение собственного Vite в этой Windows sandbox зависало. Прямой запуск Node/Vite уменьшил число дочерних процессов, однако не устранил ограничение. После законченного прогона остановлен только PID сервера, известный из вывода запуска. ОС/браузер и пользовательские процессы не менялись. Этот результат не подтверждает автоматическую очистку процессов в другой среде.

## Never run

- Живой GREEN-API/MAX: нет безопасно введённых ключей и согласованного тестового получателя.
- Реальные CORS, авторизация, тариф, лимиты, доставка, ответ и статусы.
- Визуальная сверка с оригинальным скрином задания.
- GitHub-публикация, деплой, отправка работодателю.

Снимки показывают работающую локальную форму и демо. Mock/demo не выдаются за живой MAX. Работа выполнена с AI-помощью. README и [HANDOFF.md](HANDOFF.md) описывают запуск, архитектуру и оставшуюся живую проверку.

Формат отправки и ограничения CheckAccount дополнительно сверены 3 октября с официальными страницами [SendMessage](https://green-api.com/v3/docs/api/sending/SendMessage/) и [CheckAccount](https://green-api.com/v3/docs/api/service/CheckAccount/).
